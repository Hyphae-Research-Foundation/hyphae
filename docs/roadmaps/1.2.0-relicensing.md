# Hyphae 1.2.0 relicensing plan

Status: accepted direction; implementation blocked on preflight and the
normative-specification license decision

Decision owner: Mario Gutiérrez, Celiums Solutions LLC

Decision date: 2026-08-14

Target release: `v1.2.0`

This roadmap changes the Hyphae software license from `AGPL-3.0-only` to
`Apache-2.0`. It retains `CC-BY-SA-4.0` for narrative documentation and keeps
the existing trademark policy separate. It is an execution plan, not legal
advice. The final license and contribution-governance text requires review by
qualified open-source counsel before the relicensing commit is accepted.

## Decision and immutable history

Published releases retain the terms under which they were published. Nothing
in this roadmap retroactively changes an earlier source tag, package, or
release artifact.

| Release range | Software | Documentation | Treatment |
|---|---|---|---|
| `0.1.0` through `1.0.1` | `Apache-2.0` | `CC-BY-4.0` | Immutable |
| `1.1.0` | `AGPL-3.0-only` | `CC-BY-SA-4.0` | Immutable |
| `1.2.0` onward | `Apache-2.0` | `CC-BY-SA-4.0` for narrative documentation | Proposed by this plan |

The normative specifications still require one explicit choice before the
implementation commit:

1. use `CC-BY-4.0` so third parties can implement and describe the formats
   without a ShareAlike requirement; or
2. use `Apache-2.0` for specifications as build-facing artifacts and retain
   only two repository license families.

`CC-BY-SA-4.0` is not accepted implicitly for normative specifications. The
choice, affected path set, and rationale must be frozen in a superseding ADR.

## Rationale

Hyphae is a local-first, single-node, embeddable engine. Its default product
works offline and does not include a hosted control plane, clustering, or a
SaaS boundary. The AGPL network condition therefore does not protect the
product surface that Hyphae is designed to ship, while strong copyleft creates
material adoption friction for applications embedding
`hyphae-native-product`.

Apache-2.0 matches that product shape and includes an explicit patent grant.
It does not grant rights to the Hyphae name, logos, lockup, or domains; those
remain governed by [`TRADEMARKS.md`](../../TRADEMARKS.md). The durable release
receipts, reproducible packages, signed provenance, reference implementation,
and project identity remain independent trust assets.

This decision accepts that Apache-2.0 permits proprietary and commercial
forks. It does not describe permissive licensing as a technical protection
against forks.

## P0 — fail-closed preflight

No project-license file, package manifest, SPDX header, or release metadata may
change until every item in this phase is documented.

### Dependency compatibility

Run the exact dependency and license inventory on the candidate source:

```bash
cargo deny check licenses
cargo tree --workspace --all-features --format "{p} {l}" | sort -u
```

The evidence must identify every strong-copyleft dependency and every
`GPL-2.0-only` compatibility concern. A conflicting dependency blocks the
relicensing change until it is removed, replaced, or counsel records a valid
resolution. Existing third-party license and provenance records are evidence;
they must never be mechanically rewritten as first-party project terms.

### Copyright and prior commitments

The release evidence must establish:

- the complete contributor and copyright-holder set for every file being
  relicensed;
- written authority to relicense all in-scope contributions;
- the absence, or explicit resolution, of grants, program applications,
  contracts, or public commitments that require AGPL terms; and
- counsel review of Apache-2.0 section 6 alongside `TRADEMARKS.md`.

Repository statistics such as fork counts, contributor counts, or commit
counts are observations, not proof of copyright ownership. They must be
recomputed rather than copied from the initial planning memo.

### Specification-license decision

Accept a superseding licensing ADR that selects `CC-BY-4.0` or `Apache-2.0` for
the exact normative-specification path set. The ADR must define how mixed
prose/specification files are classified and how generated contract artifacts
inherit their terms.

Exit: counsel-approved decision record, source-bound dependency inventory,
copyright authority record, prior-commitment review, and accepted
specification-license ADR.

## P1 — one coherent relicensing commit

The project-license transition must be one commit so source, policy, package
metadata, generated evidence, and release automation cannot disagree between
intermediate states.

### Root policy and notices

- replace `LICENSE` with the canonical Apache License 2.0 text;
- retain and clarify `LICENSE-DOCUMENTATION`;
- rewrite `LICENSE-POLICY.md` as an auditable per-release history;
- verify `NOTICE` against Apache-2.0 section 4(d) and retain the Celiums
  Solutions LLC copyright notice;
- regenerate `THIRD_PARTY_NOTICES.md` from the accepted dependency inventory;
  and
- supersede ADR-0025 without erasing it from the decision history.

### First-party package metadata

- set the workspace Rust license authority to `Apache-2.0` and inherit it from
  all 24 crates;
- update the TypeScript and Python package metadata, including the Python
  classifier;
- update MCP, integration, packaging, and generated-client manifests;
- update OpenAPI and JSON Schema license metadata according to the accepted
  specification decision; and
- replace first-party SPDX headers with `Apache-2.0` while preserving all
  third-party and historical-source notices verbatim.

### Documentation and contribution governance

- update the README badge and license section;
- record the immutable `v1.1.0` AGPL terms in the license history;
- remove the stale reference to the deleted `dev` branch;
- express the group-commit batching window as `138.59 ms` and distinguish it
  from contention latency;
- update release verification, SBOM, provenance, and package-content checks;
  and
- add counsel-approved contributor terms to `CONTRIBUTING.md` that preserve
  the project's future licensing options.

A DCO alone certifies contribution origin and does not grant relicensing
authority. Any CLA or copyright-assignment text is a legal control and must not
be improvised in the implementation change.

Exit: one reviewable commit in which every first-party license authority and
generated conclusion agrees.

## P2 — deterministic verification

The relicensing commit is not mergeable until all of these checks are green on
its exact SHA:

```bash
cargo deny check licenses
cargo metadata --format-version 1 --no-deps \
  | jq -r '.packages[] | "\(.name)\t\(.license)"'
rg -n "AGPL-3.0-only|GNU Affero" \
  --glob '!LICENSE-POLICY.md' \
  --glob '!docs/adr/0025-agplv3-code-and-cc-by-sa-documentation.md'
```

The final checker must use an explicit allowlist for immutable license history;
a raw expectation that `AGPL` disappears everywhere would destroy accurate
provenance. It must also verify:

- all 24 Cargo packages conclude `Apache-2.0`;
- Python, TypeScript, MCP, integration, and package manifests agree;
- source archives include the correct license bundle;
- SPDX and CycloneDX first-party conclusions agree with the source manifest;
- third-party conclusions remain unchanged and source-bound;
- all four release packages retain required notices;
- every publishable crate passes `cargo publish --dry-run` in topological
  order; and
- the complete existing CI and security matrix stays green.

Exit: exact-SHA license-policy, package, SBOM, provenance, dry-run, and hosted
CI evidence.

## P3 — `v1.2.0` release

Relicensing is part of the existing
[`1.2.0` operator and agent experience program](1.2.0-operator-and-agent-experience.md),
not an independent tag. The release remains blocked until both programs close
on one exact candidate.

The release sequence is:

1. merge the relicensing commit only after P0-P2 close;
2. complete the 1.2.0 functional, security, crash/recovery, and
   multiplatform gates;
3. create one annotated `v1.2.0` tag on the exact closed candidate;
4. publish the 24 crates in the documented topological order;
5. verify registry package license metadata and docs.rs for every library
   crate;
6. publish signed binaries, SBOMs, provenance, and attestations for all four
   targets; and
7. retain `docs/release/receipts/1.2.0.md` with source, tag, workflow,
   artifact, and registry identities.

The receipt must say whether the software is functionally identical to
`v1.1.0`; it may make that claim only if exact diff and test evidence prove it.

Exit: immutable release and registry receipts showing Apache-2.0 for every
first-party software artifact and the selected terms for normative
specifications.

## Non-claims and stop conditions

- `v1.1.0` remains `AGPL-3.0-only`; it is not withdrawn or retroactively
  relicensed.
- Apache-2.0 does not prevent commercial forks.
- The change is not represented as reversible after accepting external
  contributions under the new terms.
- A second consecutive license change is a reputational risk; the public
  per-release history must explain it directly.
- No tag, crate, Python package, plugin, binary, or GitHub Release is published
  while a license authority, exact-source binding, or 1.2.0 functional gate is
  open.
- Failure of dependency compatibility, copyright authority, prior-commitment
  review, counsel review, or specification classification stops the plan.
